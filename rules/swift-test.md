# テスト実装規約

## 適用条件

テストコード（`Tests/` 配下、`@Test` / `XCTestCase` を含むファイル）を
新規作成・変更する場面に適用する。

**他ルールとの優先順位:** 命名・インデントなどの一般規約は `swift.md`、
エラー表現は `swift-error.md` に従う。

## テストフレームワーク
- **ユニットテスト**: Swift Testing を使用する（XCTest ではない）
- **UI テスト**: XCTest フレームワークを使用する

## Swift Testing の基本
- `import Testing`、`@Test` マクロ、`#expect()` アサーションを使用する
- 非同期テストは `async throws` で実装する
- テストスイートは `struct` で定義する

## 命名規則
`テスト対象_テスト内容_期待される結果` の形式を使う。

例：`loadUser_validUserID_returnsUser`、`loadUser_invalidUserID_throwsError`

## テスト設計
- AAA パターン（Arrange / Act / Assert）で構成する
- テスト対象コードは Protocol ベースで DI 可能に設計する（Mock を注入できるようにする）
- Mock は本当に必要な場合のみ作成する

## テストカバレッジ目標
- ビジネスロジック：80% 以上
- UI ロジック：主要フローをカバー
- エラーハンドリング：異常系もテストする

## モック設計
- モックは各 `@Test` 内で新規生成する（`reset()` で再利用しない）
  - `reset()` を持つモックは「どの状態をリセットすべきか」の管理コストが生じ、リセット漏れのバグ温床になる
  - Swift Testing はテストを並列実行するため、インスタンスを共有すると競合リスクも高まる
- `reset()` を提供する場合は call recording とスタブ値の**両方**をリセットすること

## ベストプラクティス
- 1つの @Test = 1つの概念をテスト
- テストは独立している（他のテストに依存しない）
- テストデータは明示的（マジックナンバーを避ける）
- 複雑なテストは複数のサブテストに分割

## レビューチェックリスト

- [ ] ユニットテストが Swift Testing（`@Test` / `#expect()`）で書かれているか
- [ ] テストスイートが `struct` で定義されているか
- [ ] テスト名が `テスト対象_テスト内容_期待される結果` の形式になっているか
- [ ] 各テストが AAA パターン（Arrange / Act / Assert）で構成されているか
- [ ] モックが各 `@Test` 内で新規生成されているか（インスタンスを共有していないか）
- [ ] `reset()` を提供するモックが call recording とスタブ値の両方をリセットしているか
- [ ] 異常系（エラーハンドリング）のテストがあるか
- [ ] テストデータが明示的か（マジックナンバーが残っていないか）
- [ ] 1 つの `@Test` が 1 つの概念だけを検証しているか
- [ ] テストが他のテストの実行順に依存していないか
